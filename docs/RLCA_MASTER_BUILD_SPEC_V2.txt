## E. FINAL AUTOMATED PLAYER PLACEMENT MODEL

When a player registers for RLCA, do **not** ask an admin to manually decide the player's MMR or division. The application must calculate a **placement recommendation automatically**, then route the result through a staff approval workflow.

There are three distinct values:

1. **Verified 2v2 Evidence Score** — long-window evidence from Ranked 2v2.
2. **RLCA Combine Rating** — controlled league-specific signal.
3. **Starting RLCA MMR** — final custom league rating used for initial division placement.

### E1. 21-day verification window

The player must complete at least **75 completed Ranked 2v2 games** during a 21-day verification window.

Do not use:
- 1v1
- 3v3
- Casual
- Private matches
- Scrims
- Unverified self-reported values

The player must declare all known alternate accounts before placement is finalized.

### E2. Nine independent MMR snapshots

Staff/system capture **9 MMR snapshots** at unannounced checkpoints during the 21-day window. Store:
- timestamp
- account identifier
- displayed Ranked 2v2 MMR
- source / screenshot / API evidence if available
- staff/system actor
- evidence hash if a file was captured

Never overwrite an old snapshot. Corrections create a new audit entry.

Sort the nine snapshots from lowest to highest and calculate:
- **Median**
- **Peak**
- **P20**, defined for the nine observations as the second-lowest observation

Evidence Score:

`Evidence Score = (Median × 0.50) + (Peak × 0.25) + (P20 × 0.25)`

This reduces the benefit of a single spike while also preventing a player from tanking the full verification window and hiding the fact that they reached a much higher level.

### E3. RLCA Combine

After the evidence window, the player enters a controlled RLCA Combine consisting of **6 BO5 series**.

Combine controls:
- Staff/system assigns teammates and opponents.
- Players cannot choose opponents.
- Players cannot choose teammates.
- Assignments are randomized and hidden until the session begins.
- A player may not have the same teammate more than twice in the six-series set.
- All Combine series are logged with complete participants and timestamps.

For each Combine series, calculate expected team win probability using the players' pre-Combine baseline ratings. Use the actual series result minus expected probability to produce a series performance value.

`Combine Performance = average of the 6 series performance values`

Rank the 24 Season 1 players by unrounded Combine Performance.

- Lowest Combine Performance → Combine Index 0
- Highest Combine Performance → Combine Index 100
- Intermediate players → evenly spaced by rank
- Exact ties use the unrounded underlying value and deterministic player-ID tie-break only when absolutely necessary

`Combine Rating = 1000 + (Combine Index × 8)`

### E4. Final placement score

`Final Placement Score = (Evidence Score × 0.80) + (Combine Rating × 0.20)`

This means long-window Ranked 2v2 evidence is the dominant signal and the controlled Combine provides a secondary league-specific signal.

### E5. Starting RLCA MMR

After all 24 players have a Final Placement Score, rank them from lowest to highest.

`Starting RLCA MMR = 1000 + ((Rank - 1) ÷ 23 × 800)`

Therefore:
- Rank 1 = 1000
- Rank 24 = 1800
- All other players are spaced evenly between them

This is the ONLY approved Season 1 starting MMR formula.

### E6. Initial tier placement

The lowest-to-highest mapping is:

- **Ranks 1–8 → RLCA Contender Division**
- **Ranks 9–16 → RLCA Challenger Division**
- **Ranks 17–24 → RLCA Master Division**

This creates exactly 8 players per active division.

### E7. Initial roster construction

Because each franchise must contain exactly one player from each active division, the draft should be run independently by player pool:

- 8 Contender players → one assigned to each franchise
- 8 Challenger players → one assigned to each franchise
- 8 Master players → one assigned to each franchise

Use the configured draft method (Season 1 snake draft or another approved draft configuration) but enforce the one-per-division roster rule server-side. A team can never draft a fourth player or a second player from the same initial tier while another division slot remains unfilled.

## F. FINAL RESET / RE-RUN BEHAVIOR

The phrase “reset a player” must mean **restart a formal placement/evaluation cycle**, never “manually set the player's number lower.”

When an admin starts a **Reverification / Re-Placement**:

1. Preserve the player's existing career history.
2. Create a new evaluation cycle with a unique evaluation ID.
3. Capture a new 21-day Ranked 2v2 evidence window.
4. Require a new minimum of 75 verified Ranked 2v2 games.
5. Capture 9 new MMR snapshots.
6. Run the same evidence formula.
7. Run a new 6-series Combine if the season/league configuration requires it.
8. Recalculate the Final Placement Score.
9. Recalculate the proposed RLCA MMR.
10. Recalculate the proposed division.
11. Show the old and new values side-by-side.
12. Require an authorized staff approval before the new placement becomes official.

A reset never deletes the old rating history. The old rating remains queryable in the audit/history tables.

For a completely new season, create a new PlayerSeason record and rerun the configured preseason placement process rather than mutating Season 1 history.

## I. WAIVER AND FREE-AGENT TIMING

The exact anti-abuse timing must be explicit.

### New-player activation
A newly activated player cannot be moved to FA or Waiver until the 7-day activation hold has completed, unless an approved staff exception exists.

### Rostered-player release
When a franchise releases a rostered player, the normal release path is:

`ROSTERED → WAIVER`

The waiver period is **7 full days** unless the league configuration is changed for a future season. During the waiver period, eligible franchises can submit claims.

If unclaimed after the full waiver period:

`WAIVER → FREE_AGENT`

A Free Agent may then be signed by an eligible franchise through the normal transaction workflow.

### No bypassing
A franchise cannot mark a player directly as Free Agent to skip the required waiver period unless an authorized staff exception is explicitly recorded.

# 6. Qualification Points — exact production rules

Keep **Qualification Points** separate from RLCA MMR.

RLCA MMR measures player competitive rating.

Qualification Points determine team season qualification.

## Regular season
- Official BO5 win = **5 points** to the team
- Officially recorded tie = **2.5 points to each team**
- Loss = **0 points**

A normal BO5 cannot end in a tie. A 2.5-point tie can only exist if league staff officially records the result as a tie under an approved ruling.

## Major 1 and Major 2 points

| Finish | Points |
|---|---:|
| 1st | 240 |
| 2nd | 180 |
| 3rd | 140 |
| 4th | 100 |
| 5th | 60 |
| 6th | 40 |
| 7th | 20 |
| 8th | 10 |

The winning team receives 240 points. The displayed event card should say **“Top Award: 240 Points.”**

## Last Chance points

Last Chance uses exactly **half the normal Major placement values**:

| Finish | Points |
|---|---:|
| 1st | 120 |
| 2nd | 90 |
| 3rd | 70 |
| 4th | 50 |
| 5th | 30 |
| 6th | 20 |

The event card should say **“Top Award: 120 Points.”**

## Points behavior

All qualification points remain on the season total.

There is no reset after a Major.

A lower team must always have a mathematical path to recover through later regular-season wins and event points, unless the remaining maximum points make qualification mathematically impossible.

The standings engine should calculate and expose:
- Current total points
- Maximum possible remaining points
- Mathematical qualification status
- Mathematical elimination status
- Locked status

Never use a manually typed “qualified” label if the database can determine it.

# 8. Last Chance — exact logic

At the end of Major 2, the qualification table is frozen for the purpose of creating the Last Chance field.

### Seeds 1 and 2 are locked

The teams currently ranked #1 and #2 by qualification points **before Last Chance are permanently locked into Championship Seeds #1 and #2**.

Last Chance results cannot remove them from Championship.

Their seed number cannot change.

### Seeds 3–8 enter Last Chance

The lowest six teams enter the Last Chance event.

## Last Chance bracket

First round:
- Seed 3 vs Seed 8
- Seed 4 vs Seed 7

Seeds 5 and 6 receive byes.

Second round:
- Seed 5 plays one first-round winner
- Seed 6 plays the other first-round winner

Final:
- The two second-round winners play the Last Chance Final

Use deterministic seeding so the pairings are stable and visible before play begins.

Placements:
- Final winner = 1st
- Final loser = 2nd
- Semifinal losers = 3rd/4th
- First-round losers = 5th/6th

Award half-value Last Chance points according to that finish.

Because the Last Chance is 5 total series, it can fit into two Sundays while honoring the maximum of two official series per team per Sunday.

# 9. Championship qualification — exact logic

After all Last Chance points are added, calculate final Season 1 Qualification Points.

### Locked teams

The two teams locked before Last Chance remain:
- Championship Seed #1
- Championship Seed #2

### Remaining four spots

Take teams 3–8 from the pre-Last-Chance standings.

After Last Chance, rank those six teams by **final total season points**.

The top four among those six become Championship Seeds #3–#6.

Therefore the Championship field is exactly:
- Seed 1 — locked
- Seed 2 — locked
- Seed 3 — highest remaining final points
- Seed 4 — second-highest remaining final points
- Seed 5 — third-highest remaining final points
- Seed 6 — fourth-highest remaining final points

The Championship is **always exactly 6 teams**.

# 16. Replay storage / cleanup / backup

Do not store replay files on Vercel's application filesystem.

Use object storage for raw replay files and PostgreSQL/Supabase for metadata and league state.

Keep the database data durable even after raw replay files are removed.

### Permanent data

Keep permanently:
- Seasons
- Teams
- Players
- Rosters
- MMR history
- Roster Value history
- Qualification points
- Match records
- Game scores
- Player statistics
- Brackets
- Transactions
- Eligibility records
- Staff decisions
- Audit logs
- AI analysis summaries
- Replay checksums
- Replay-derived structured data

### Replay retention

Do not keep every raw replay forever.

Create a retention policy with categories:

**Permanent raw replay:**
- Championship
- Major 1
- Major 2
- Last Chance
- Officially disputed matches
- Matches selected as notable/feature matches

**Sampled regular-season raw replay:**
- Keep a configurable sample from regular-season weeks
- Default target can be 10–20% of regular-season matches
- Random sampling must be deterministic and recorded so it cannot be manipulated afterward

**Temporary raw replay:**
- All other regular-season replays remain available until parsing and validation complete
- After the retention period, delete the raw file but keep metadata and derived stats

Never delete a replay that is under an active dispute, review, investigation, or unresolved technical issue.

### Season backup

At season rollover, create an immutable season archive:
- Full database logical export
- Season JSON snapshot
- Brackets
- Standings
- Player history
- Team history
- Transactions
- MMR history
- Point history
- Staff decision/audit history
- Replay manifest

Store the archive outside the primary production runtime.

Maintain a backup manifest containing:
- Season ID
- Snapshot time
- Export version
- File hashes
- Database migration version
- App build version
- Replay retention manifest

The system must support creating a new active season without overwriting old seasons.

Season pages must remain accessible after a new season begins.

Use an `activeSeasonId`/`active_season_id` concept rather than hardcoding Season 1 everywhere.

Every season must be queryable and restorable independently.

If using Supabase, remember that database backups do not automatically back up objects stored through Supabase Storage, so replay/object backups must be handled separately.

# 38. Final implementation rule

When there is a conflict between UI assumptions and the official league rules, the database/rules engine wins.

When there is a conflict between a Discord message and the database, the database wins.

When there is a conflict between an AI recommendation and the rules engine, the rules engine wins.

When a calculation can be derived from source records, never store a manually editable copy as the primary source of truth.

Everything should be designed so that RLCA can run Season 1 now and still support Season 2, Season 3, more teams, more tiers, more events, more franchises, and deeper analytics without rewriting the application.

Build the league as a real product, not a one-season demo.

## 51. EXACT STATUS LOGIC FOR THE 7-DAY WAIT

Implement time calculations on the server using UTC timestamps.

Display league-local time in the UI.

Do not count “seven calendar days” loosely.

The eligibility time is:

`activated_at + INTERVAL '7 days'`

Until the current server time is at or beyond `eligible_change_at`, direct move to FA or Waiver is denied by the transaction engine.

The UI should show:

**Eligible in 5d 3h 21m**

Do not allow client-side clocks to decide eligibility.

## 52. WAIVER CLAIM ORDER

Use deterministic waiver order.

Recommended Season 1 order:
- Lowest current qualification-point team in the same division first
- Then next-lowest
- Continue upward

On successful claim, the claiming team moves to the bottom of the current waiver order.

The exact order must be stored in the database so it can be audited.
